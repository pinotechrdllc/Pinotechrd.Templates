# MyApp

<!--#if (modular) -->
MyApp is a .NET 10 API organized as a modular monolith: one host composes the business modules, each a bounded context with clean architecture layers inside, and every module builds on the same shared building blocks. It was generated from the `pinotechrd-app` template.

## Modules

Each module is a bounded context under `src/Modules/{Name}/`, with the five projects above. The module name is a PascalCase C# identifier of ASCII letters and digits (a name such as `Ñandú` is rejected at startup); `Access` is reserved, because every project already has the Access module (`--module Access` generates it twice and does not build); the template creates one module (`--module`, `Core` by default), and a later version of the template adds a script to create more.

- Composition. A module is one class that implements `IModule` (from the web building block) in its Endpoints project: `MyModuleModule`. Its `AddServices` registers the services of every project of the module (the handlers of its Application with `AddHandlers`, later its persistence). The host lists each module once, in `src/MyApp.Api/BusinessComposition.Modular.cs`, with `builder.AddModule<MyModuleModule>()` (the Access module, shared by both architectures, is added first, in `BusinessComposition.cs`); a module added twice is registered and mapped once. `AddServices` receives a `ModuleContext` with the host's `Services`, `Configuration` and `Environment`; it runs at startup and during the build-time contract generation, so it must not need a configuration value or a database to run (`ModuleContext.IsGeneratingApiDocument` is true only during that generation, to skip the start-time validation of a setting that needs a secret). It also registers the permissions the module's endpoints require, with `context.Services.AddPermissions(...)`.
- Endpoints. An endpoint of the module is a public class that implements `IEndpoint` in its Endpoints project, one per use case, with its request and response types next to it. It is found by scanning that project and mapped under `/api/v1/{module}`, where `{module}` is the module name in kebab case (`Sales` gives `/api/v1/sales`, `SalesOrders` `/api/v1/sales-orders`, `HRPayroll` `/api/v1/hr-payroll`), and tagged with the module name (an endpoint that calls `WithTags` replaces that tag with its own). Routes are written relative to that prefix: `routes.MapPost("/orders", ...)` serves `/api/v1/sales/orders`. Host endpoints come first in the API contract, then the modules by name, each one's endpoints in the order of their full type names. A module whose route segment is also the first segment of a host endpoint's route (a module `Version` next to `GET /api/v1/version`) stops the application at startup with an error naming the module.
- Validation. `MyModuleModule.AddServices` calls `AddValidation()` and must keep doing so: the built-in validation is generated only for the endpoints mapped in the project that makes the call, so without it the module's request bodies are not validated (see [Errors](#errors)). A project has exactly one `AddValidation()` call site: a second one in the same project fails the build (CS8785).
- Contracts. A module's Contracts project holds only interfaces, records and enums: what other modules may call or receive. The only other type allowed is its assembly marker, `MyModuleContractsAssembly`. HTTP request and response types are not contracts; they live with their endpoint.
- Boundaries. The Application, Infrastructure and Endpoints projects of a module may reference another module's Contracts project and nothing else of it; its Domain and Contracts projects reference no other module at all. Each module owns its own tables; no module reads another module's data.

## Build and test

```sh
dotnet build MyApp.slnx
dotnet test MyApp.slnx
```

Run the API with `dotnet run --project src/MyApp.Api`. It needs a PostgreSQL connection string (see [Database](#database)) and a JWT signing secret (see [Authorization](#authorization)). It starts with the launch profile in `src/MyApp.Api/Properties/launchSettings.json`: the Development environment, so user secrets and `appsettings.Development.json` are read and the OpenAPI document is served, at `http://localhost:5180` (a free port chosen when the project was generated; change `applicationUrl` there to use another). With the database running, these answer 200:

```sh
curl http://localhost:5180/health/live
curl http://localhost:5180/health/ready
curl http://localhost:5180/api/v1/version
curl http://localhost:5180/openapi/v1.json
```

`dotnet run --no-launch-profile`, a published build and a container run in Production: no user secrets and no `/openapi/v1.json`. The OpenAPI document is served, to anonymous callers, in every environment except Production: Development, Staging and any other name.

The tests need Docker: they start PostgreSQL in a container, and they fail, rather than skip, when Docker is not running.

## Dependencies

Package versions live in one file, `Directory.Packages.props`; project files name packages without a version. Transitive pinning is on, so a version listed there also applies when the package arrives through another package.

- **Lock files.** Every project has a `packages.lock.json` with the exact version and content hash of every package it uses, direct and transitive. The first restore of a new project writes them. Commit them, and commit their changes together with every version change. They have the same content on Windows and Linux (only the line endings differ, and git normalizes those).
- **Locked restore in CI.** When `CI` or `TF_BUILD` is `true` (GitHub Actions and Azure Pipelines set them), or with `-p:ContinuousIntegrationBuild=true`, restore runs in locked mode: if a project file or `Directory.Packages.props` no longer matches the lock files, it fails with `NU1004` instead of resolving other versions. Locked mode writes a missing lock file instead of failing, so the pipeline should also fail when restore leaves the working tree changed (`git status --porcelain` not empty).
- **Updating a package.** Change its version in `Directory.Packages.props` (or run `dotnet package update <Id>`), run `dotnet restore` outside CI to update the lock files, build, test, and commit both. A new package gets a `PackageVersion` entry there and a `PackageReference` without a version in the project.
- **Publishing for a runtime.** A locked restore with `-r linux-x64` fails with `NU1004` unless the lock files already have that runtime, in the published project and in every project it references: set `RuntimeIdentifiers` for all of them (in `Directory.Build.props`) and restore once before committing the lock files.

### Security advisories

Every restore checks every package, direct and transitive, against the GitHub Advisory Database through nuget.org (NuGet audit, at every severity). A finding is a warning from `NU1901` (low) to `NU1904` (critical) with the link to the advisory. `NU1900` or `NU1905` means the vulnerability data could not be read, for example offline. All of these are warnings in a local build, so a new advisory does not stop unrelated work, and errors in CI, so nothing merges with a known advisory or an audit that did not run. When one appears:

1. A package you reference: raise its version in `Directory.Packages.props` to a release that fixes the advisory (`dotnet package update --vulnerable` does it for every affected package).
2. A transitive package: `dotnet nuget why MyApp.slnx <Id>` shows which package brings it. Prefer a release of that package that no longer depends on the affected version. Otherwise add a `PackageVersion` for the affected package, at the fixed version, to `Directory.Packages.props`: transitive pinning makes every project use it (a pin can raise a version, not lower it).
3. No fix released: read the advisory. If it does not apply to how the project uses the package, suppress that advisory alone with `<NuGetAuditSuppress Include="https://github.com/advisories/GHSA-..." />` in an `ItemGroup` of `Directory.Build.props`, with a comment that says why, and remove it when a fix ships.

Then restore, build, test and commit the updated lock files.

## Database

The application uses PostgreSQL through Npgsql. `src/BuildingBlocks/MyApp.BuildingBlocks.Infrastructure/Database/` owns the connection: one `NpgsqlDataSource` for the whole process, a singleton disposed with the host, which holds the connection pool. Every later piece of data access (EF Core, the tenant schema selection) is built on that data source.

### Connection string

The connection string is the setting `ConnectionStrings:Database`. It is a secret: it is never in `appsettings.json` or `appsettings.Development.json` (a test fails if a connection string appears there), never logged and never returned in an error or a health response. Supply it through the environment, `ConnectionStrings__Database`, in every deployment (from the platform's secret store), or through user secrets on a development machine.

A local PostgreSQL, with the same major version the tests use:

```sh
docker run -d --name app-postgres -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app -e POSTGRES_DB=app -p 127.0.0.1:5432:5432 postgres:17.7
```

It publishes the port on the loopback address only: Docker Desktop opens a published port past the host firewall, and this password is trivial.

Then, for that container (local values only):

```sh
dotnet user-secrets init --project src/MyApp.Api      # once; user secrets are read in the Development environment
dotnet user-secrets set "ConnectionStrings:Database" "Host=127.0.0.1;Port=5432;Database=app;Username=app;Password=app" --project src/MyApp.Api
```

or, for one shell session, `export ConnectionStrings__Database="Host=127.0.0.1;Port=5432;Database=app;Username=app;Password=app"` (PowerShell: `$env:ConnectionStrings__Database = "..."`).

Use `Host=127.0.0.1`, not `localhost`: the port is published on IPv4 only, and on Windows `localhost` tries `::1` first, whose refused connection takes about 2 seconds, so `/health/ready` would answer 503 with the database up.

### Fail fast

When the host starts it checks the setting: a missing or empty value, one that Npgsql does not accept as a connection string (bad format, unknown keyword, invalid value, no `Host`), or one that sets a refused setting (see [Connection settings](#connection-settings)), stops it with an `OptionsValidationException` that names `ConnectionStrings:Database` and never shows the value; the exit code is 1. The check does not connect: a valid string for a server that is down starts the application, and the readiness probe reports the database.

The build-time contract generation (`dotnet build src/MyApp.Api -p:UpdateContract=true`) starts the host with no configuration and no server, so it skips this check; the services are still registered and nothing connects to the database.

### Connection settings

Set on every connection by the application:

| Setting | Value | Why |
| --- | --- | --- |
| `Include Error Detail` | always off, even if the connection string turns it on | Error details can carry row values into exceptions, and exceptions reach the logs. |
| `Persist Security Info` | always off, even if the connection string turns it on | The connection string read back from a connection or the data source (by EF Core or an interceptor, for example) never holds the password. |
| `Application Name` | the application name (`MyApp.Api`) unless the connection string sets one | Each instance's connections are identifiable in `pg_stat_activity`. |
| `Command Timeout` | 30 seconds unless the connection string sets one | No statement waits without a limit chosen on purpose. |
| `Maximum Pool Size` | 20 unless the connection string sets one (Npgsql's default is 100) | The pool is per process, and 100 alone fills PostgreSQL's default `max_connections` of 100: four instances at 20 use 80 and leave room for the migrator, the reserved superuser slots and an operator. |

Left at Npgsql's defaults, which the connection string can override: pooling on, `Minimum Pool Size` 0, `Connection Idle Lifetime` 300 seconds, `Timeout` (to connect, including the server's first reply and the login) 15 seconds, `Cancellation Timeout` (how long a cancelled command waits for the server to confirm before the connection is broken) 2000 milliseconds. No retry policy is configured.

To raise the pool, add `Maximum Pool Size=40` (for example) to the connection string, and keep instances × `Maximum Pool Size`, plus the migrator and other clients, below the server's `max_connections`; raise that on the server first if needed. A request that finds the pool full waits for a free connection up to `Timeout`, then fails.

Refused in every project, with or without tenants, when the host starts (an `OptionsValidationException` that names the setting), and by tenant contexts and the migrator for any other data source:

| Setting | Why |
| --- | --- |
| `Multiplexing=true` | The commands of one connection run on whichever physical connection is free, so session state set on one (the tenant's `search_path`) is not there for the next command. |
| `No Reset On Close=true` | A connection would return to the pool with its session state, the tenant's `search_path` included, for the next user. |
| `Search Path`, or `search_path` in `Options` (also written with escapes, such as `search\_path`), or in the environment variable `PGOPTIONS` | Every connection would start, and return after a reset or a rollback, with that schema, so code that uses no tenant would see it, and a tenant connection could fall back to it. Only the setting name counts (`-c name=value`, `-cname=value`, `--name=value`, read with escapes and `-` as `_`): `-c statement_timeout=...` or `-c application_name=search_path_app` stay allowed. |

Allowed after review: `Pooling=false`, prepared statements (`Max Auto Prepare`), several hosts with `Load Balance Hosts` or `Target Session Attributes`, lifetimes and keepalives, and `Enlist` (Npgsql's default, `true`): a tenant context refuses to open its connection inside an ambient `TransactionScope`, the one case where the tenant's schema would be set inside a transaction whose rollback undoes it; keeping the default means a `TransactionScope` around tenant code fails loudly instead of silently not covering it. Session defaults that no connection string shows are checked by every tenant connection when it opens: a new session's `search_path` must be PostgreSQL's default (`"$user", public`), with no schema named like the database user, so a default set with `ALTER ROLE ... SET search_path`, `ALTER DATABASE ... SET search_path`, in `postgresql.conf`, or by the role `PGUSER` chooses, stops the tenant connection. The message names no role or database (it is logged and kept in the exception's data under `PgDbRoleSetting`, for operators). Managed services that ship a database-level default such as `"$user", public, extensions` make every tenant open fail closed this way: the operator runs `ALTER DATABASE <db> RESET search_path` (or `ALTER ROLE <role> IN DATABASE <db> RESET search_path`, whichever `pg_db_role_setting` shows) and reconnects; installed extensions that lived in `public` then move to `extensions` (see Extensions). Nothing can detect a physical connection initializer that sets `search_path` on a data source built by hand, or PgBouncer in transaction pooling mode: do not use either.

With PgBouncer, use session pooling: the tenant's schema is set per connection (see [Tenancy and persistence](#tenancy-and-persistence)), and in transaction pooling mode that session state does not follow the client between transactions.

Npgsql writes no log events: its debug events name the host, the database and the commands, so no logger factory is given to it. Errors reach the caller as exceptions.

### Readiness

`/health/ready` takes a connection from the shared pool and runs `SELECT 1`. It answers 200 `Healthy` when the database answers and 503 `Unhealthy` when it does not, and it always answers within the check's 2-second limit plus the request's own processing (measured 2.00 to 2.22 seconds): when the connection is refused, when the address does not route, when a server accepts the connection and never replies, and when the server stalls in the middle of the query. Npgsql does not stop for a cancellation while it waits for a new connection's first reply and login (it waits up to `Timeout`), and a cancelled query waits up to `Cancellation Timeout` more, so the check stops waiting at 2 seconds and lets that attempt finish on its own: it keeps one pool slot until Npgsql gives up (at most `Timeout`, 15 seconds, for a silent server; `Cancellation Timeout`, 2 seconds, after the limit for a stalled query) and then releases it. Probes made meanwhile wait on that same attempt instead of starting another, so readiness never holds more than one connection, and once the database answers again the next probe after that attempt ends reports 200. `/health/live` never touches the database. The body is only the status word: no host, user, connection string or exception. A failing check is logged at Error by the health check service with a fixed description that holds only the exception type and, for a server error, its SQLSTATE code (for example `28P01`, a failed login), because Npgsql's messages name the host and the user.

## Tenancy and persistence

Each tenant's data lives in a PostgreSQL schema of its own, and every module owns its tables, its EF Core context and its migrations inside that schema. The code is in `src/BuildingBlocks/MyApp.BuildingBlocks.Infrastructure/Tenancy/`; the read-only `ICurrentTenant` is in the application building block.

- The current tenant. `ICurrentTenant` (scoped) gives the tenant's opaque id and its schema, or reports that the scope has none. Business code only reads it. Setting it is infrastructure work: `ICurrentTenantInitializer.Initialize(tenantId)` (infrastructure building block), called once per scope by the code that knows the tenant from a trusted source (the request pipeline after authentication, from the token's tenant claim: see [Authorization](#authorization); `ITenantJobRunner`; the migrator). Setting the same tenant again does nothing and setting another one throws. Nothing is static or ambient, so a tenant never reaches another request or work running in parallel in another scope. Per-tenant background work goes through `ITenantJobRunner.ForEachTenantAsync(work, ct)` (infrastructure building block): it takes no tenant id, lists the in-service tenants from `ITenantDirectory.ListInServiceTenantIdsAsync`, and runs the work for each, one at a time, in a new scope whose tenant is set for it; a failure of the work comes back in the tenant's outcome.
- A module's context. The module's Infrastructure project calls `services.AddTenantDbContext<SalesDbContext>("Sales")` from its registration. An optional callback adds further options; it runs first, and the tenant configuration (data source, history table, naming, guard) is applied after it, so it cannot replace them; the guard checks them again when the context first opens a connection. A context built elsewhere, such as a library's context or one a message framework builds outside dependency injection, gets the same behaviour with `optionsBuilder.UseTenantPersistence(dataSource, currentTenant, "Sales")` (or `UseTenantPersistence(scopedServices, "Sales")`). The context runs on the one shared data source (never a pool of its own) with snake_case names, and a guard binds each connection it opens to the current tenant: `search_path` becomes the tenant's schema followed by the shared `extensions` schema and `pg_temp` (named last, so a temporary table never shadows a tenant table), and is read back together with `current_schema()`. Without a current tenant the open fails with `InvalidOperationException` before anything reaches the server: there is no fallback to `public`. If the tenant's schema does not exist, or setting it fails or is cancelled, the connection is closed before the error goes on, so no connection of the context stays open on another schema. Resolve the context from a scope whose tenant is set. Tenant contexts are never pooled (`AddDbContextPool`): a pooled context would keep the tenant of its first scope.
- Raw SQL. Through EF Core (`ExecuteSqlRaw`, `SqlQueryRaw`, `FromSql`), tenant SQL never changes the session. The guard reads each command with PostgreSQL's lexical rules (comments, string constants of every kind, dollar quotes, quoted identifiers read as their name) and refuses a statement that starts with `DISCARD ALL`, `RESET ALL`, `RESET` or `SET [SESSION|LOCAL]` of `search_path`, `schema`, `role`, `session_authorization`, `SET SESSION AUTHORIZATION`, `SET standard_conforming_strings`, or `ALTER ROLE|USER|DATABASE|SYSTEM` (not `ALTER USER MAPPING`); any `set_config` call, quoted or schema-qualified, unless its first argument is one plain string constant followed by a comma that names another setting (`set_config('app.user_id', ...)` passes, `set_config('search_' || 'path', ...)` does not); any write to `pg_settings` (`UPDATE`, `INSERT INTO`, `DELETE FROM`, `MERGE INTO`, qualified or quoted, also inside a CTE or `PREPARE`; an `UPDATE` of that view runs `set_config`); and any `U&"..."` identifier. Reading `pg_settings`, a table such as `pg_settings_log` and a column named `pg_settings` pass. `DISCARD PLANS`, `DISCARD TEMP` and `DISCARD SEQUENCES` pass, as do a column named `reset_token` or `search_path` and a literal 'RESET ALL'. Every tenant connection also requires `standard_conforming_strings` on, PostgreSQL's default, because the check reads strings that way. This check is a guard against mistakes in application SQL, not a security boundary: it cannot see SQL that runs inside the server (functions and procedures, `DO` blocks, dynamic `EXECUTE`), nor commands run directly on the connection from `OpenTenantConnectionAsync`. For a connection, use `await context.Database.OpenTenantConnectionAsync()`: EF opens it, so it is bound to the tenant, and the context owns it (close it with `Database.CloseConnectionAsync()` or leave it to the end of the scope). This is the one supported way; opening `Database.GetDbConnection()` yourself throws, and the context refuses any command on a connection its guard did not bind, or whose settings are refused (each connection object is checked, including one set later with `SetDbConnection`). Commands run directly on that connection (Dapper, `NpgsqlCommand`) get no statement check: they follow the same rule, unchecked.
- Transactions. Use the context's own transactions (`Database.BeginTransactionAsync`): the connection is bound when it opens, before the transaction begins, so a rollback (or a rollback to a savepoint) cannot undo the binding. A `TransactionScope` is refused when it is active as the context opens its connection (the connection would enlist and the binding would run inside the scope's transaction). Two tenant contexts of one scope (so of one tenant) share a transaction only by sharing the connection: `await first.Database.OpenConnectionAsync()`, then `second.Database.SetDbConnection(first.Database.GetDbConnection())`, `var tx = await first.Database.BeginTransactionAsync()` and `await second.Database.UseTransactionAsync(tx.GetDbTransaction())`. The second context accepts the connection because it is bound to the same tenant; a context of another tenant refuses it. Between modules prefer integration events: modules do not share tables.
- No schema in the model. A tenant context never names a schema: no `HasDefaultSchema`, no schema in `ToTable`, `SplitToTable`, `ToView`, `ToFunction`, `HasDbFunction`, a stored procedure or a sequence, and none in the migrations. One model then serves every tenant, and the connection decides where the tables are. The migrator refuses a context whose model names a schema; it cannot check raw SQL in a migration (`migrationBuilder.Sql`), so that SQL must not name a schema either. Prefix table names with the module (`sales_orders`); no foreign keys or joins across modules.
- Extensions. Declare a PostgreSQL extension in the model without a schema (`modelBuilder.HasPostgresExtension("citext")`). Before migrating tenants, the migrator installs every declared extension, once, into the shared schema `extensions` (with `CASCADE`, so the extensions it requires go there too), which every tenant connection sees after its own schema; the migration's own `CREATE EXTENSION IF NOT EXISTS` is then a no-op. Installing an extension needs the right on the database (a superuser, or a trusted extension and `CREATE` on the database): where the migrator's role lacks it, an administrator creates the schema `extensions` and the extensions there first (the migrator then only checks them). An extension already installed in another schema stops the migrator with the statement to move it, or, for an extension that cannot be moved, with how to recreate it. Tenant connections run as the tenant's role, which has only `USAGE` on `extensions` (through the database's group role `t<database oid>_shared`), so tenant code cannot create objects there (see [Database roles and deployment](#database-roles-and-deployment)). A tenant connection whose role cannot use `extensions` fails when it opens, instead of silently comparing `citext` as `text`.
- Migrations. They live in the module's Infrastructure project, next to its context, in a `Migrations` folder. Each module has its own history table, `__ef_migrations_<module>` in snake case (`Sales` gives `__ef_migrations_sales`, `SalesOrders` `__ef_migrations_sales_orders`), unqualified, so it sits in the tenant's schema. Two module names that give the same history table (`Sales` and `SALES`) are refused. To create migrations with `dotnet ef migrations add`, give the module an `IDesignTimeDbContextFactory` that returns `new SalesDbContext(TenantPersistenceRegistration.DesignTimeOptions<SalesDbContext>("Sales"))`: the same provider, naming and history table, with no connection. Keep the naming convention forever: changing it renames the history columns.
- The migrator. `services.AddTenantMigrator()` registers `ITenantMigrator`. For a tenant it creates the schema if it is missing and applies each module's pending migrations, the module `Access` first and then the others by name, under an advisory lock per tenant held on a connection of its own (which turns `idle_session_timeout` off for itself, and is checked before each module). Concurrent runs on one tenant take turns, each migration is applied once, and a run with nothing pending applies nothing. `MigrateAsync(tenantIds, maxDegreeOfParallelism)` migrates several tenants and reports each one, a failed tenant included, without stopping the others. A tenant's run holds two connections, so the migrator runs at most `(Maximum Pool Size - 1) / 2` tenants at once (at least one), whatever the requested degree, and refuses a pool smaller than 2 (when the migrator is first resolved, with a message naming `Maximum Pool Size`). Migrations never run when the API starts; they are a separate deploy step. It needs PostgreSQL 16 or later (tenant roles, see [Database roles and deployment](#database-roles-and-deployment)).
- Shared contexts and the catalog. A context that is not tenant-scoped is registered with `services.AddSharedDbContext<CatalogDbContext>("catalog")` (`src/BuildingBlocks/MyApp.BuildingBlocks.Infrastructure/Migrations/`): on the same shared data source, snake_case names, no tenant guard, and its history table `__ef_migrations_<schema>` in its schema. Its model keeps every object in that one schema (`HasDefaultSchema`); the database migrator refuses one that maps a table elsewhere. The Access module's `CatalogDbContext` maps the security package's five catalog tables (tenants, subscription plans, system subscriptions, plan modules, plan features) with the same settings as the package, and owns their migrations; `AccessDbContext` maps the same tables and excludes them from its migrations (the tenant migrator skips a table excluded from migrations when it looks for a schema in a tenant model). A test checks that both mappings agree with the migrated catalog.
- The migrator command. `src/MyApp.Migrator` is a console program, never part of the API: `dotnet run --project src/MyApp.Migrator` with the same connection string as the API (`ConnectionStrings__Database` in the environment, user secrets in Development, or `--ConnectionStrings:Database=...`). Under one global advisory lock (`DatabaseMigrator.GlobalLockKey`, on a connection of its own, so two runs take turns and each migration is applied once) it migrates the shared contexts in registration order (the catalog), reads every tenant id from `catalog.tenants` (all rows, by id) before any tenant starts, then migrates the tenants with `ITenantMigrator`, each under its own tenant lock, at most `Migrator:MaxDegreeOfParallelism` at once (default 4, at least 1, also capped by the pool). A failed catalog stops the run before any tenant; a failed tenant does not stop the others. It writes one line for the catalog, one per tenant (its id and the migrations applied, or the failure), one for the plans seeded in the catalog (see Seeding) and a summary, never a connection string, and exits 0 when everything is up to date, 1 when something failed, 2 when a setting is missing or invalid (nothing is migrated), 130 when it was cancelled (Ctrl+C, a stop signal): it reports the cancellation, releases its locks, and what finished stays applied, so running it again completes the rest. A tenant row whose id is the empty GUID fails alone, named by its id; the other tenants still run. The pool needs at least 3 connections (the global lock and one tenant's two): a pooled connection string with a smaller `Maximum Pool Size` is an invalid setting (exit 2). A shared context's model keeps every object (tables, views, functions, sequences, extensions, enums, ranges, collations) in its schema, and a tenant table never holds a foreign key to the catalog or to a table that names a schema. The composition is `src/MyApp.Migrator/MigratorComposition.cs`; the persistence of other modules or layers joins it through its partial hooks, as in the API's `BusinessComposition.cs`.
- Provisioning a tenant. `dotnet run --project src/MyApp.Migrator -- provision --Provision:Slug=acme --Provision:Name=Acme --Provision:SubscriptionId=<id>` (the subscription must exist in `catalog.system_subscriptions`; run the migrator without a command first, or it exits 1 asking for it). It writes the `catalog.tenants` row first, as provisioning, with a new id and the schema `tenant_<id>` (never derived from the slug), then creates and migrates that schema under the tenant's lock and marks the row active. The slug is the key: the same slug, name and subscription again reports "already provisioned", or resumes a tenant a failed or interrupted run left provisioning (each attempt that ends in a failure or an activation is counted in `provisioning_attempts`; a run that finds the tenant already activated by a concurrent one counts nothing and reports it as already provisioned; a failure leaves only its SQLSTATE or exception type in `provisioning_error`); another name or subscription is `tenant_slug_taken`, and a suspended or cancelled tenant is refused unchanged. Concurrent runs for one slug end with one tenant and each migration applied once. The slug is 1 to 63 lower-case letters, digits or single hyphens, starting and ending with a letter or digit; the name is 1 to 200 characters without control, invisible format or separator characters. An invalid or missing setting, an unknown command, `provision` anywhere but first, an argument that is not a setting, or a `Provision` setting without the command exits 2 and the report never quotes the value (ADR 0011).
- Seeding. <a id="seeding"></a>Every `migrate` keeps the data that follows the code in step with it (ADR 0013); `provision` seeds its tenant the same way, not the plans. In each tenant, after its migrations and under its lock, as the migrator's login: one `security_modules` row per module of the `PermissionCatalogue` (the first segment of its permissions, code upper case, id `SecurityModuleId.FromCode`), one `security_permissions` row per permission (code `ACCESS.USERS.READ`, id `SeedIds.Permission`), and, when the tenant has the system role `Administrator` (id `SeedIds.AdministratorRole`, never matched by name), every permission granted to it, so a newly declared permission reaches it and one removed by hand comes back. In the catalog, once it is migrated, the plans `OPERATOR` (every module) and `STANDARD` (every module except `Platform`), with one report line `Plans: N plan(s) and M plan module(s) added.`. It only adds, with `INSERT ... ON CONFLICT DO NOTHING` and parameters: rows made by hand are matched by code and kept, and nothing is changed or removed (stale rows stay until removed by hand). Modules and permissions are matched by code and must also carry the deterministic id of that code (plans link modules by `SecurityModuleId.FromCode`): a row with the code but another id, or with the id but another code, fails the tenant with a message naming the code, and its seeding is rolled back; plans are adopted by exact code. A seeding failure fails the tenant (or, for the plans, the run: exit 1) like a failed migration. Another module seeds its own tenant data with an `ITenantSeeder` registered by `services.AddTenantSeeder<T>()`.
- Bootstrap. <a id="bootstrap"></a>After `migrate`, `dotnet run --project src/MyApp.Migrator -- bootstrap --Bootstrap:Slug=operator --Bootstrap:Name=Operator --Bootstrap:AdminEmail=<email>` creates the operator tenant and its first administrator (ADR 0013). The password comes only from the environment (`Bootstrap__AdminPassword`) or user secrets: on the command line or in any `appsettings*` file it is refused (exit 2, never echoed). When given it must be 15 to 256 characters (Unicode scalar values) and not only white space, and the email only letters a-z or A-Z, digits and `- . _ @ +` (Identity's user name rule, as the user name is the email), both checked before any write (exit 2); the password is required only when the administrator does not exist yet (exit 2, naming the setting). Once the catalog is up to date the command seeds the plans, the operator's subscription (plan `OPERATOR`, linked to the tenant through `tenant_name`, the package's convention), provisions the tenant like `provision` (the operator subscription is reserved: `provision` refuses it with `tenant_subscription_reserved`), then creates in it the system role `Administrator` with every permission and the user (user name and email the given email, email confirmed) in that role. It is idempotent and runs under an advisory lock of its own, so concurrent runs take turns: a user with that email is never changed and its password never reset, so a second run with another password exits 0 and changes nothing; a run with another slug, or with another email once the administrator exists, exits 1 and changes nothing. Identity's refusals are reported by their codes only; the email and the password never appear in the report, the logs or an error. Passwords anywhere in the Access module are Identity V3 hashes with 210 000 iterations, 15 to 256 Unicode scalar values, no composition rule (`AddAccessPasswordPolicy`, with `AccessPasswordValidator`). `Bootstrap` settings without the command are refused (exit 2), like `Provision` settings.
- Creating a migration. The tool is pinned in `.config/dotnet-tools.json` (`dotnet tool restore` once), and the migrator is the startup project: `dotnet ef migrations add <Name> --project src/Modules/Access/MyApp.Modules.Access.Infrastructure --startup-project src/MyApp.Migrator --context AccessDbContext --output-dir Persistence/Migrations` (for the catalog, `--context CatalogDbContext --output-dir Persistence/Catalog/Migrations`; for the Data Protection key ring, `--project src/BuildingBlocks/MyApp.BuildingBlocks.Infrastructure --context DataProtectionKeysDbContext --output-dir DataProtection/Migrations`). Each context has an `IDesignTimeDbContextFactory` with the run-time naming and history table and no connection. Do not pass `--namespace`: the model snapshot would land in another folder (ADR 0001). Generated migrations are code generated by the tool (an `.editorconfig` next to them says so): regenerate them, never edit them by hand.
- Schema names. A tenant's schema is `tenant_` followed by its id as 32 hexadecimal digits (`TenantSchemaName.For`), so it is unique per tenant and never derived from a name a user chose. Every schema name is checked against `^[a-z][a-z0-9_]{0,62}$` before it is used in SQL, and sent as a parameter or quoted.
- Pooled connections. A connection keeps the tenant's `search_path` until it returns to the pool, where Npgsql resets the session before the next user: `DISCARD ALL`, or, when the connection holds prepared statements (Npgsql keeps them across uses), `RESET ALL` and the release of advisory locks and temporary objects, which also clear `search_path`. PostgreSQL plans a prepared statement again when `search_path` changes, so prepared statements do not cross tenants. The readiness probe and any other code that uses the data source directly need no tenant and see no tenant's tables. The binding statement, which also reads the session's default `search_path` and the right to use `extensions`, costs one round trip per open and is not traced, like the readiness probe's query. Throughput: a scope that opens a new connection for every query pays the bind each time (measured about half the queries per second: 526/s against 1,070/s). Hold the connection for the request or the unit of work instead: `await context.Database.OpenConnectionAsync()` (or `OpenTenantConnectionAsync`) at the start, and EF reuses it until the scope ends.
- Residual risk, as built. Each tenant connection runs as its tenant's role, so PostgreSQL itself refuses schema-qualified SQL on another tenant's schema (`FromSqlRaw("SELECT * FROM tenant_b.users")` from tenant A fails with 42501) and any object created in `extensions` (42501). What remains: every tenant's schema name is visible in `pg_namespace`; the tenant role can write its own module history tables; every tenant role reads all rows of the shared catalog tables the tenant contexts map (through the group role), so schema-qualified SQL from one tenant reads the other tenants' `tenants`, plan and subscription rows; and the login can leave the role (`RESET ROLE`, `SET ROLE` to another tenant's role it is a member of), so this stops mistakes, not hostile SQL: the defence against that is having no SQL injection. Only a login per tenant would be a hard boundary (rejected for cost: one server connection per tenant). The statement check refuses `SET ROLE`, `RESET ROLE` and `set_config('role', ...)` in application SQL through EF.
- PgBouncer. Session pooling only. In transaction pooling mode the `search_path` set when the connection opened does not follow the client to the next transaction.

### Database roles and deployment

Roles belong to the whole PostgreSQL cluster, so every role name is scoped to its database by the database's oid (`pg_database.oid`), which the migrator and the connection guard both read: each tenant has a `NOLOGIN` role `t<database oid>_<id as 32 hex digits>` (`TenantRoleName.For`, from the id like the schema, never from the slug), such as `t16384_0f8fad5bd9cb469fa16570867728950e`, and each database a group role `t<database oid>_shared` (`TenantRoleName.SharedFor`). Two databases on one server, migrated by the same or different logins, never share a role. The migrator creates it on every run (migrate and provision) and grants it `SELECT`, `INSERT`, `UPDATE`, `DELETE` on every table of its schema (and `USAGE`, `SELECT` on its sequences), now and, through default privileges, for tables later migrations create; `USAGE` on its schema and never `CREATE`; and membership in the database's group role, which has `USAGE` on `extensions` and `SELECT` on the shared tables the tenant contexts map (the catalog tables `AccessDbContext` reads). The migrator's login keeps ownership of the schemas and tables. The application's login becomes a member of each tenant role `WITH INHERIT FALSE, SET TRUE`: it gains none of the role's rights by itself, and the guard assumes the role in the same statement that sets `search_path`, then checks `current_user`. The pool's reset gives the login back its own role. The migrator's own tenant connections keep the migrator's login.

- Two logins, the recommended deployment. The migrator connects with a login that owns the database and has `CREATEROLE` (no superuser needed; installing extensions may need one, see Extensions). The API connects with a plain `LOGIN` that owns nothing and has no rights on tenant schemas: run the migrator with `Migrator:ApplicationRole` (`Migrator__ApplicationRole`) set to the API's login name. Each process reads its own `ConnectionStrings:Database`. The readiness probe needs no rights.
- The catalog for the application's login. Before login, and on every authenticated request, the API reads `catalog.tenants` on a connection that assumes no tenant role, as its own login (the tenant from `X-Tenant`, whether the token's tenant is active; see [Authorization](#authorization)). On every `migrate` run, once the catalog is migrated, the migrator grants `Migrator:ApplicationRole` `USAGE` on the schema `catalog` and `SELECT` on the columns `id`, `identifier` and `status` of `catalog.tenants`, nothing else of the catalog (the columns are declared with `services.AddApplicationRead(...)` in `AddAccessCatalog`). With the setting empty nothing is granted: the application uses the migrator's login, which owns the tables. A named login that does not exist fails the catalog step, and so the run (exit 1). Deploy the migrator before an API version that reads the catalog, or the API answers 500 on those requests.
- The Data Protection key ring for the application's login. The API reads and adds its keys in `data_protection.keys` (see [Data Protection keys](#data-protection-keys)). On every `migrate` run, once that schema is migrated, the migrator grants `Migrator:ApplicationRole` `USAGE` on the schema `data_protection`, `SELECT` on `id`, `friendly_name`, `xml`, `signature` and `signer` and `INSERT` on `friendly_name`, `xml`, `signature` and `signer` of `data_protection.keys`, never `UPDATE` or `DELETE` (declared with `services.AddApplicationRead(...)` and `services.AddApplicationAppend(...)` in `AddDataProtectionKeyStore`). Run the migrator before the first API version that stores its keys there: until then the API cannot read or create a key.
- One login, as in development: leave `Migrator:ApplicationRole` empty and that login receives the memberships.
- Privileged logins. A tenant connection refuses a login that is a superuser or has `BYPASSRLS` (it reads every tenant's data whatever role it assumes), unless `Tenancy:AllowPrivilegedLogin` (`Tenancy__AllowPrivilegedLogin`) is `true`. `appsettings.Development.json` sets it, because development and the single-login setup typically use a superuser; leave it off in production. It always refuses a login that inherits a tenant role (a membership `WITH INHERIT TRUE`, directly or through another role), which would read the tenant's data without assuming the role. The migrator's own tenant connections are not checked.
- Existing roles. On every run, for every tenant role and the shared role (also roles the migrator created itself, or a concurrent run created meanwhile), the migrator stops, naming the role and the unexpected row, when the role has `LOGIN`, `SUPERUSER`, `BYPASSRLS`, `CREATEROLE`, `CREATEDB` or `REPLICATION`, or when `pg_auth_members` holds any row for it (as role or as member) other than these:
  - the creator's row: the migrator's login (`current_user`) `WITH ADMIN`, granted by the bootstrap superuser, which PostgreSQL 16 records when a login that is not a superuser creates a role;
  - rows without `ADMIN` granted by the migrator's login (or by the bootstrap superuser when that login is a superuser): a tenant role a member of the database's shared role; the application login (`Migrator:ApplicationRole`, or the migrator's login when empty) a member of a tenant role `WITH INHERIT FALSE, SET TRUE`; a tenant role of the same database a member of the shared role.
  So a role precreated by another login (which keeps `ADMIN` on it), granted to another role or login, or granted to the application login with `INHERIT TRUE` is never adopted. Revoke the row (`REVOKE ... GRANTED BY ...`, as a superuser for rows granted by the bootstrap superuser) or drop the role, then run the migrator again.
- PostgreSQL 16 or later: the migrator checks the version and that the named login exists, and stops with a message otherwise.
- Order of deployment: run the migrator before deploying an API version that assumes roles. A tenant whose role does not exist (created before roles) fails when its connection opens, with a message asking to run the migrator; a login that is not a member is told to set `Migrator:ApplicationRole` and run the migrator. Running the migrator again changes nothing.
- Restoring or copying a database. The restored database gets a new oid, so its role names change: run `migrate` after a restore, before the API serves it (until then its tenants fail to open with a message asking to run the migrator). The roles of the old oid are orphaned: drop them when no database uses them any more (`DROP OWNED BY` then `DROP ROLE` in the database they belonged to). Dropping a tenant's role is not done yet (no deprovisioning).
- Changing the migrator's login. The login that created the roles holds `ADMIN` on them and granted their memberships, so another migrator login finds rows it does not establish and stops (see Existing roles). Keep one migrator login per database; to switch, a superuser drops the database's tenant and shared roles (`DROP OWNED BY` then `DROP ROLE`, in that database) and the new login runs the migrator, which creates them again. Changing `Migrator:ApplicationRole` likewise needs the old login's memberships revoked first.

## Authorization

The API denies by default. The code is in `src/BuildingBlocks/MyApp.BuildingBlocks.Web/Authorization/`, registered by `builder.Services.AddApiAuthorization()` in `Program.cs`; the read-only `ICurrentUser`, `IPermissionChecker` and the `PermissionCatalogue` are in the application building block (`Identity/`, `Security/`).

The Access module (`src/Modules/Access`) wires the `Pinotechrd.Security` package: JWT bearer is the default scheme, and a request with a valid access token (HMAC-SHA256 signature with the secret `Access:Jwt:Secret`, issuer `Access:Jwt:Issuer`, audience `Access:Jwt:Audience`, not expired) is authenticated; anything else on an endpoint that is not anonymous answers 401 `unauthorized` with `WWW-Authenticate: Bearer`, never a redirect, and an authenticated user without the permission 403 `forbidden`.

### Sign-in and sessions

The endpoints are in `src/Modules/Access/MyApp.Modules.Access.Endpoints/Auth/`, on the port `IAccessAuthentication` (Application) implemented by `AccessAuthentication` (Infrastructure) over the package. Login, refresh and logout are anonymous and take the tenant's slug in the `X-Tenant` header (`.TenantFromHeader()`); change-password needs an access token.

| Endpoint | Body | Answer |
| --- | --- | --- |
| `POST /api/v1/access/auth/login` | `{ "email", "password" }` | 200 `{ "accessToken", "expiresAt" }` and the refresh cookie. Every refusal is the same 401 `invalid_credentials`, without a cookie: unknown or inactive tenant, unknown user, wrong password, locked or inactive account. |
| `POST /api/v1/access/auth/refresh` | none (the cookie) | 200 as for login, with a new cookie; the old token is spent. Every refusal is 401 `invalid_refresh_token` and drops the cookie. A spent token presented again ends its whole session and is logged as a warning. |
| `POST /api/v1/access/auth/logout` | none (the cookie) | 204 whether or not the cookie holds a valid token: ends the cookie's session when the token is found, and drops the cookie. A request refused before the endpoint runs (400 `bad_request` for a missing or repeated `X-Tenant`, 403 `csrf_rejected`, 429 `rate_limited`) neither ends the session nor drops the cookie. |
| `POST /api/v1/access/auth/change-password` | `{ "currentPassword", "newPassword" }` | 204: every session of the user ends (refresh tokens revoked, security stamp renewed) and the cookie is dropped. A wrong current password answers 400 `validation_failed` on `currentPassword` and counts towards the lockout; a locked account gets the same answer; a password the policy refuses (`AccessPasswordPolicy`) answers 400 on `newPassword`; a concurrent change of the same user that won answers 409 `conflict`. |

- The refresh token travels only in the cookie `__Host-refresh`: `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, no `Domain`, `Max-Age` the sliding lifetime (`Access:Jwt:RefreshTokenExpiryDays`); never in a body. `SameSite=Strict` means a browser client must be served from the same site as the API (a proxy in front of both, Phase 6); another site's pages never send the cookie.
- CSRF. Login, refresh and logout refuse with 403 `csrf_rejected` a request whose `Origin` is neither the request's own origin nor one of `Http:Cors:AllowedOrigins` (`null` included), and a request whose `Sec-Fetch-Site` is neither `same-origin` nor `none` unless its `Origin` is listed in `Http:Cors:AllowedOrigins`. A request with neither header (not a browser) passes. To accept a front end on another origin, list it in `Http:Cors:AllowedOrigins`.
- Rate limit. The four endpoints share the stricter named policy `auth` (`HttpRateLimiting.AuthPolicy`, `Http:RateLimiting:Auth`, 10 requests per minute per client by default) on top of the global limit; a rejection is 429 `rate_limited` with `Retry-After`.
- Timing. An unknown tenant or user is checked against a dummy password hash, so it costs a hash like a real account; the lookups and the lockout bookkeeping still take different time, so the answer is not constant time.
- Logs. Sign-in succeeded and failed, refresh token reuse (warning), logout and password change, with only the user's id (when known) and the tenant's id: never the email, the slug, a token or the cookie.
- Lockout uses Identity's clock (the system clock); it cannot be moved by an injected `TimeProvider`.

- One source of truth for claim types. The settings `Identity:UserIdClaimType` (default `sub`) and `Identity:TenantIdClaimType` (default `tenant_id`) decide what the API reads, and the Access module makes the package agree: the tokens it issues carry the user's id in the user claim (the package's own `id` claim is never read, so a token with `id` and no `sub` answers 401), its tenant claim is `Identity:TenantIdClaimType`, and the bearer handler keeps every claim under the name it has in the token (`MapInboundClaims` off). The package takes the tenant claim type once, when the module is registered: a value that differs at start (set by a configuration source added later) stops the host with a message that names both values. Tokens also carry the email, a display name and the user's permissions at login; the API reads none of them and never logs them.
- Permissions are read from the database on every check, not from the token. The checker of `Access` (`SecurityEnginePermissionChecker`) asks the package's engine: `Access.Users.Read` is granted when the tenant's subscription is active, its plan includes the module `ACCESS`, and the user's roles grant the code `ACCESS.USERS.READ` (codes are stored in upper case) or a per-user allow does, with no per-user deny; a deny wins. Roles and role permissions, and the per-user allows and denies, come from the tenant's own tables (only active permissions of active modules, none for an inactive user). A deactivated user's access token, a stateless JWT, still authenticates `AuthenticatedOnly()` endpoints until it expires, while every permission check refuses that user from the next request. The package caches the subscription and module answers for 15 minutes per process: a subscription or plan change can take up to that long to apply on each instance.
- The tenant the package sees is the request's tenant from the token: a step at `AuthenticatedRequestStepOrder.SecurityContext` (-150) copies it into the package's `TenantContext`. The package's own tenant resolution middleware is not used (it accepts a tenant from a header for anonymous requests).
- Persistence. The users, roles and permissions live in each tenant's schema, through `AccessDbContext` on the shared data source (`AddTenantDbContext`, history table `__ef_migrations_access`); the catalog tables of the package (tenants, plans, subscriptions) are in the shared schema `catalog`. The tenant tables are created by the module's migrations (`Persistence/Migrations`, `InitialAccess`), which add to the library's model foreign keys from `role_permissions` to `roles` and from `user_permissions` to `users` (cascading) and one row per role or user and permission (ADR 0010); the catalog tables are excluded from them and created by the catalog's own context, `CatalogDbContext` (`Persistence/Catalog`, history table `catalog.__ef_migrations_catalog`), which the migrator runs first (see [Tenancy and persistence](#tenancy-and-persistence)). Tenants are provisioned with the migrator's `provision` command, the operator tenant and its first administrator with `bootstrap` (see [Bootstrap](#bootstrap)); the migrator seeds the modules, permissions and plans (see [Seeding](#seeding)).

- Deny by default. Every endpoint under `/api/v1` requires an authenticated user (the route group calls `RequireAuthorization()`), and a fallback policy requires one for any other routed endpoint without authorization metadata. An unknown route still answers 404 `not_found` and a wrong method 405 `method_not_allowed`. `/health/live`, `/health/ready`, the OpenAPI document and `GET /api/v1/version` allow anonymous callers explicitly.
- Nothing follows the pipeline except endpoints. Right after authorization the pipeline answers every request that matched no endpoint (404) or the wrong method (405) itself, so middleware added after `app.UseApiPipeline()` (`app.Use`, `app.Run`, static files) is never reached by a request authorization did not check. Middleware that must serve requests without an endpoint, such as static files, goes before `UseApiPipeline()` and is public.
- Declaring access. Each routed endpoint, under `/api/v1` or not, except the health probes and the OpenAPI document, declares exactly one of the following on the endpoint itself:
  - `.RequirePermission("Sales.Orders.Read")`: an authenticated user that holds the permission; 401 for an anonymous caller, 403 `forbidden` for a user without it.
  - `.AuthenticatedOnly()`: any authenticated user, no permission checked (an operation on the caller's own data).
  - `.AllowAnonymous()`: anyone, logged in or not.

  `RequirePermission` and `AuthenticatedOnly` refuse a route group (`ArgumentException`), so an endpoint added to a group later never inherits an access it does not state. `AllowAnonymous()` on a group cannot be told apart from one on each endpoint by the start-time check: do not call it on a group. `ShortCircuit()` skips authorization, so only an `AllowAnonymous()` endpoint mapped outside the `/api/v1` group may use it (the group's authorization metadata makes routing refuse a short-circuit with a 500, so the start refuses it first). Endpoints use the default authentication scheme only: an authorization that names its own `AuthenticationSchemes` (`RequireAuthorization(policy)` with schemes, `[Authorize(AuthenticationSchemes = ...)]`) would make authorization authenticate again with them and replace the user after the identity steps set the current user and tenant from the default scheme, so the start refuses it.
- Permission names. `{Module}.{Resource}.{Action}`, three PascalCase segments of ASCII letters and digits: `Access.Users.Read`, `Sales.Orders.Export`. Lower case (`access.users.read`), two or four segments, empty segments, spaces, other punctuation and letters outside ASCII are rejected with an `ArgumentException` where the name is written, so the application does not start.
- The catalogue. Each module registers the permissions its endpoints require from its `AddServices`, and the host its own from `Program.cs`, with `services.AddPermissions("Sales.Orders.Read", "Sales.Orders.Export")`. `PermissionCatalogue`, a singleton, holds them all, each once; the seeding of roles and permissions reads it.
- The start-time rule. When the host starts, after every endpoint is mapped and before the server listens, it checks every routed endpoint (a route written without its leading slash included) except the health probes and the OpenAPI document. No declaration, more than one, permission metadata without the requirement that enforces it, a required permission that is not in the catalogue, a short-circuited endpoint that is not anonymous, an endpoint whose authorization names its own `AuthenticationSchemes`, two registered permissions that differ only by case, two checkers for one module or a checker registered as `IPermissionChecker` itself, no scheme to challenge or forbid, or a real scheme registered while the placeholder is still the default to authenticate or challenge, stop it with an `InvalidOperationException` whose message lists every offender (endpoints by method, route and name). The exit code is 1. The build-time contract generation builds the same pipeline, so it fails the same way. Endpoints added by tests (through `IEndpoint`) follow the same rule.
- The permission checkers. Each module that owns permissions registers one checker for them, keyed by its name, the first segment of the permission: `services.AddPermissionChecker<AccessPermissionChecker>("Access")` answers `Access.Users.Read`. `RequirePermission` asks `PermissionCheckerRouter`, which calls the checker of the permission's module with the current user and the exact permission string, and denies a permission whose module has no checker. With no checker registered every permission-protected endpoint answers 403 to an authenticated user; a registered permission without a checker is denied, not refused at start. A generated project has one checker, the Access module's, for `Access.*`. Two checkers for one module (ignoring case) and a checker registered as `IPermissionChecker` itself stop the start.
- The current user. `ICurrentUser` (scoped) gives `IsAuthenticated` and `UserId`, an opaque GUID read from the claim `Identity:UserIdClaimType` (default `sub`); `UserId` throws when there is no authenticated user. Claims are read only from the authenticated identities of the principal, and the claim type is compared exactly, case included (`SUB` is not `sub`). An authenticated principal without exactly one such claim holding a GUID in its standard form with nothing around it (`xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`) answers 401 on an endpoint that is not anonymous; on an anonymous endpoint it is treated as anonymous, with no user and no tenant. A JWT handler that renames inbound claims (the platform's maps `sub` to a long URI unless `MapInboundClaims` is off) must keep `sub`, or the setting must name the claim it produces.
- The current tenant. For an authenticated request the tenant comes from the token only, the claim `Identity:TenantIdClaimType` (default `tenant_id`, a GUID), and is set through `ICurrentTenantInitializer` for that request's scope alone (see [Tenancy and persistence](#tenancy-and-persistence)); a tenant in a header, the query string or the body is never read. The claim follows the same reading rules as the user's. An authenticated principal without one valid tenant claim answers 401 on an endpoint that is not anonymous; on an anonymous endpoint the request goes on as anonymous, with no user (`ICurrentUser.IsAuthenticated` is false) and no tenant from the token. An anonymous request has no tenant, except on an endpoint marked `.TenantFromHeader()` (login, refresh, logout): there a step at `AuthenticatedRequestStepOrder.TenantSelection` (-250) reads the tenant's slug from the `X-Tenant` header. The header is required on such an endpoint (missing or sent twice answers 400 `bad_request`) and ignored everywhere else. Its tenant is set only when the slug names an active tenant of the catalog (`ITenantCatalog`, implemented by the Access module on `CatalogDbContext`); a value that is not a valid slug, an unknown slug and a tenant that is provisioning, suspended or cancelled all leave the request without a tenant, the same way, so the endpoint answers its usual failure and nobody learns which slugs exist. Without an `ITenantCatalog` registered the request fails (500). The marker requires `AllowAnonymous()`: on any other endpoint the host does not start. When the header has set a tenant, the token's tenant must be the same one: another one answers 401. The wiring is `builder.Services.AddRequestTenancy()` in `Program.cs` (`src/MyApp.Api/TenancyComposition.cs`), because only the host may set the tenant.
- Inactive tenants. A token whose tenant is no longer active (provisioning, suspended or cancelled) answers 403 `tenant_unavailable` on every endpoint, anonymous ones included (fail closed: the token's tenant is already set for the request and is never dropped), from the next request: the Access module's step at `AuthenticatedRequestStepOrder.TenantStatus` (-175) reads the tenant's status from the catalog once per authenticated request, without a cache. Activating the tenant again lets its tokens through at once.
- The extension point. Between authentication and authorization the pipeline runs every registered `IAuthenticatedRequestStep` in ascending `Order`: the built-in steps first (the current user at -300, the tenant from the `X-Tenant` header at -250, the tenant from the token at -200, the Access module's tenant status at -175 and security context at -150, the identity on the log event and the span at -100), then the application's (zero or more; two steps with the same order stop the start). A step sees the authenticated principal and the matched endpoint, runs for every request that matched an endpoint except the health probes, and can answer the request itself (a problem document, or `TypedResults.Challenge()` for a 401): then no later step, no authorization and no endpoint run. A per-user or per-tenant rate limit belongs here. Register one with `services.AddAuthenticatedRequestStep<MyStep>()`; steps are singletons and read scoped services from `context.RequestServices`.

The settings are in the `Identity` section and validated at start (a blank claim type stops the host):

| Setting | Default | Why this default |
| --- | --- | --- |
| `Identity:UserIdClaimType` | `sub` | The subject claim of a JWT (RFC 7519), an opaque identifier, never a name or an email. |
| `Identity:TenantIdClaimType` | `tenant_id` | The tenant claim the security package reads from its tokens. |

The JWT settings are in the `Access:Jwt` section, read when first used and validated at start: a missing secret, a secret shorter than 32 bytes in UTF-8, or a missing issuer or audience stops the host with an `OptionsValidationException` (the messages name them `PinotechrdSecurityOptions.Jwt.*`, never the value). The build-time contract generation runs with no configuration, so there the module uses a random throw-away key, and the contract depends on no setting.

| --- | --- | --- |

Refresh tokens are stored in the tenant's schema (`DatabaseRefreshTokenStore`, replacing the package's in-memory store), so they survive a restart and every instance shares them: tables `refresh_token_families` (one per sign-in session) and `refresh_tokens` (only the SHA-256 of each token, never the token), without a tenant column, so a token of another tenant is not found. Every expiry is decided by the database clock (`now()`): keep the API's and the database's clocks synchronised. A refresh consumes its token in one statement, so of two concurrent refreshes with one token exactly one succeeds; presenting a consumed token again revokes its whole session (RFC 9700, section 4.14.2), and a logout revokes the session of its token. A background service (`RefreshTokenPurgeService`, on every instance) deletes the families whose session ended or that were revoked more than a grace period ago, with their tokens, tenant by tenant (Active and Suspended ones) in small batches; a tenant-wide advisory lock lets one instance purge a tenant at a time, and a tenant whose schema or role is missing is logged and skipped. A tenant whose purge finds the lock held 24 rounds in a row is logged as a warning (any role with SQL access can hold an advisory lock).

Accounts lock after 10 failed sign-ins in a row, for 15 minutes, new accounts included (`AccessPasswordPolicy`). The count is exact for wrong current passwords at change-password (one atomic update each) and for sign-ins made one after another; failed sign-ins sent in parallel can lose counts inside the package's password check, so a burst may need more than 10 attempts to lock (the auth rate limit still bounds it). A locked account's refresh also fails, and the package consumes the token before it checks the lockout: anyone who knows an email can end that user's sessions at their next refresh (within the 10-minute access token) and keep them out for 15 minutes. That is the price of stopping password guessing; the sign-in endpoints also have a per-client rate limit (`Http:RateLimiting:Auth`).

Two-factor sign-in is disabled: the API offers no second step, and the package's two-factor attempt store is replaced by `DisabledTwoFactorAttemptStore`, which throws when an attempt is counted, so a code is never accepted (it fails closed). The package's in-memory store would make the host refuse to start outside Development. To enable two-factor sign-in, turn it on for a user through `UserManager.SetTwoFactorEnabledAsync`, which renews the security stamp and so ends the user's existing sessions (setting the column directly leaves the existing refresh tokens valid); then map `MapTwoFactorAttempts` in the security model, register `AddPinotechrdEfTwoFactorAttemptStore<AccessDbContext>()` in `AccessModule` instead of the disabled store, add the migration for the `two_factor_attempts` table with `dotnet ef`, and add the endpoint of the second step (a task in PLAN.md).


PowerShell: `dotnet user-secrets set "Access:Jwt:Secret" ([Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(48))) --project src/MyApp.Api`.

## Errors

Error responses produced by the pipeline (an unknown route, a malformed request, a validation failure, an unhandled exception) and failures an endpoint returns through `ToProblem()` are RFC 9457 problem details documents, served as `application/problem+json` whatever the request's `Accept` header. An unhandled exception is logged, and the response is always a 500 `internal_error` with no exception details. A body an endpoint writes itself, such as `Results.BadRequest("text")` or `Results.Conflict(obj)`, is not converted: return every failure through `ToProblem()`.

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.1",
  "title": "Bad Request",
  "status": 400,
  "detail": "The name is too long.",
  "errors": { "name": ["The name is too long."], "lines[1].quantity": ["Must be positive."] },
  "code": "name_too_long",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736"
}
```

`code` is the contract that clients and translations key on. `title` is the name of the status, the same for every response with that status: "Bad Request" for every 400, a validation failure from the built-in validation or from a validation `Error` included, and "Unprocessable Content" for 422. `errors` appears only on validation errors. `traceId` correlates the response with the logs. An endpoint returns a failed result with `ToProblem()`, which maps the `ErrorKind` to the status: `Validation` 400, `Unauthorized` 401, `Forbidden` 403, `NotFound` 404, `Conflict` 409, and `Failure` 422 Unprocessable Content when a business rule rejects the operation. A returned error is expected and never answers 500; 500 `internal_error` is reserved for exceptions. A body that is not valid JSON or does not match the expected shape answers 400 `invalid_json`; any other malformed request (a missing or unparsable route, query or header value, or a missing body) answers 400 `bad_request`.

```csharp
routes.MapGet("/things/{id}", Results<Ok<Thing>, ProblemHttpResult> (int id) =>
{
    Result<Thing> result = Find(id);
    return result.IsSuccess ? TypedResults.Ok(result.Value) : result.Error.ToProblem();
});
```

The keys of `errors` name the fields as they appear in the request JSON: each segment of the property path follows the API's JSON naming policy (camelCase by default), and dots and indexes are kept (`homeAddress.street`, `lines[1].quantity`). This applies to both sources: the built-in validation, which reports C# property paths, and the `Details` of a validation `Error`, so either form can be used when building one.

Request types are validated with DataAnnotations by the built-in minimal API validation (`AddValidation()`). It is generated at compile time for the request types of the endpoints mapped in the project that calls `AddValidation()`, wherever those types are declared (a contracts project included). A separate project that maps its own endpoints must call `AddValidation()` in its own registration code, or its request types are not validated; the calls add up.

Codes are string constants in classes whose names end in `ErrorCodes` (`CommonErrorCodes` and `HttpErrorCodes` to start). Every code is listed in `contract/problem-codes.v1.md`. Codes are only ever added, never renamed. `request_failed` is the generic fallback and may be replaced by a specific code for a status later.

## API contract

`contract/openapi.v1.json` is the OpenAPI description of the API, frozen in the repository. Clients generate their types from this file, not from a running server, and any change to the API surface shows up as a diff in it. It lists every operation under `/api/v1` by its endpoint name (`WithName`, which becomes the `operationId`) and the problem details schemas, where `title`, `status`, `code` and `traceId` are required. Each operation declares the problem responses the pipeline can return for it: 500 always; 400 when it takes parameters or a body; 408, 413 and 415 when it takes a body; 401 when it requires authentication (every operation that is not `AllowAnonymous()`), and 403 as well when it requires a permission; 429 (with its `Retry-After` header) unless the endpoint opts out of rate limiting with `DisableRateLimiting()`. The document declares the HTTP bearer security scheme `Bearer`, and every operation that requires authentication references it in its `security`; anonymous operations reference none. Unknown routes and wrong methods are not operations, so their 404 and 405 are not listed. An endpoint declares the errors it returns itself (404, 409, 422) with `ProducesProblem`, for example `.ProducesProblem(StatusCodes.Status404NotFound)`. Health probes are not part of it.

Regenerate it after changing an endpoint, a request or a response, and commit it together with the code change:

```sh
dotnet build src/MyApp.Api -p:UpdateContract=true
```

It builds only that architecture and writes `contract/openapi.v1.clean.json` or `contract/openapi.v1.modular.json`; without `ContractArchitecture` the build fails. The contract is generated, and compared with the served document by its test, with the .NET SDK that `global.json` selects: `10.0.100` or a later 10.0 SDK, the latest installed feature band (`rollForward: latestFeature`), so two machines can select different SDKs (`dotnet --version` in the project folder shows which). Different SDK versions can emit slightly different schema text for the same API. If the contract test fails only because of such text, with no change to the API, regenerate the contract with the SDK that CI selects and commit it; if two feature bands keep producing different documents, make every machine and CI select the same one, for example by setting `version` in `global.json` to that SDK with `rollForward: latestPatch`. Outside Production the running API also serves the same document at `/openapi/v1.json`, for inspection.

## Logging and telemetry

`builder.AddTelemetry()` in `Program.cs` sets up both; the code is in `src/BuildingBlocks/MyApp.BuildingBlocks.Web/Telemetry/`.

### Logs

Logs are an event stream on standard output, one JSON object per line, in every environment (Serilog's compact format). The platform collects them (`docker logs`, Kubernetes, the cloud's log agent); the application writes no files and sends logs nowhere else.

```json
{"@t":"2026-11-18T06:15:09.99Z","@m":"HTTP GET /api/v1/boom responded 500 in 25.4461 ms","@i":"776c4006","@l":"Error","@tr":"c146d631ea7bb66213c14a1a9ae9d332","@sp":"acfd2052f6e05710","RequestRoute":"/api/v1/boom","RequestMethod":"GET","RequestPath":"/api/v1/boom","StatusCode":500,"Elapsed":25.4461,"SourceContext":"Serilog.AspNetCore.RequestLoggingMiddleware","Application":"MyApp.Api","Environment":"Production","Version":"1.0.0"}
```

`@t` is the time, `@m` the rendered message, `@l` the level (absent for Information), `@x` the exception, `@tr` and `@sp` the trace and span ids of the current activity. Every event carries `Application`, `Environment` and `Version`. `@tr` is the `traceId` of a problem response for the same request, so an error a client reports leads to its log lines and its trace.

Each request writes exactly one completion event when it ends, with `RequestMethod`, `RequestPath` (without the query string), `RequestRoute` (the route template, when an endpoint matched), `StatusCode` and `Elapsed` in milliseconds. Its level is Error for a 5xx or an exception, Information otherwise, 4xx included: a 4xx is the client's outcome and scanners produce them in bulk, so count them by `StatusCode` instead. Health probes write it at Verbose, which is off, so polling does not flood the logs. An unhandled exception is logged once, with its stack trace, by the exception handler; the completion event of that request is at Error. If the exception happens after the response has started (part of the body was sent), the exception handler logs it once, the connection is aborted so the client sees an incomplete response, and the completion event is at Error with the status that was actually sent and no exception.

After authentication, the completion event of a request also carries `UserId` and `TenantId`, the opaque GUIDs of the current user and tenant, each only when it is known; an anonymous request has neither. They are set by a built-in step of the pipeline (see [Authorization](#authorization)); nothing else of the token or the principal is logged, never a name, an email, a token or a header value.

The levels come from the standard `Logging:LogLevel` section: `Default` for every category, and a category name (such as `Microsoft.AspNetCore`) for every category that starts with it. Values are `Trace`, `Debug`, `Information`, `Warning`, `Error`, `Critical` and `None`; an invalid value stops the application at start. Provider sections (`Logging:Console`) and wildcards in category names are not read. Override them with environment variables:

```sh
Logging__LogLevel__Default=Debug
Logging__LogLevel__Microsoft.AspNetCore=Information   # names with dots work in Docker and Kubernetes, not in a POSIX shell's export
```

The levels and the OTLP switch below are read once, at start: a configuration source added later or a reload of `appsettings.json` does not change them. Restart the application to apply a change.

Some framework categories write a header value, the query string or the client address. They stay at `Warning` when `Default` or a parent such as `Microsoft.AspNetCore` is raised, and change only when the category itself is named (`TelemetryRegistration.PinnedLogCategories`):

| Category | What it writes below Warning |
| --- | --- |
| `Microsoft.AspNetCore.Hosting.Diagnostics` | "Request starting" (Information) with the query string. The completion event replaces it. |
| `Microsoft.AspNetCore.HttpOverrides` | "Unknown proxy" (Debug) with the client address and port; "Unparsable IP" (Debug) with the raw `X-Forwarded-For` value. |
| `Microsoft.AspNetCore.Cors` | "The request has an origin header" (Debug) and "Request origin ... does not have permission" (Information) with the `Origin` value; a refused preflight names the requested headers. |
| `Microsoft.AspNetCore.Server.Kestrel.BadRequests` | "bad request data" (Debug) quoting the rejected part of the request, such as a `Host` header value or the request line. |

Naming one of them, for example `Logging__LogLevel__Microsoft.AspNetCore.HttpOverrides=Debug` to debug a proxy setup, is a deliberate choice that writes those values to the logs; do it briefly and not where the logs are kept for long.

If the application cannot start (an invalid setting, for example) it writes one Fatal event with the exception in the same format and exits with code 1. A failure while the host starts (a hosted service or a setting validated at start) is written once, by the host, as "Hosting failed to start" at Error, and the exit code is 1. A shutdown signal that arrives while the host starts is not a failure: the exit code is 0 (the host still logs its "Hosting failed to start" event with the cancellation).

A test or another piece of code can receive the events by registering a Serilog `ILogEventSink` (or `ILogEventEnricher`) as a service; nothing in the building block changes.

### Secrets and personal data

No log event and no span attribute may contain a header value (`Authorization`, `Cookie`, `Set-Cookie` or any other), a query string, a request or response body or the client address: they carry tokens, session cookies and personal data. At the shipped levels, and with `Default` or `Microsoft.AspNetCore` raised to any level, none of them is logged or recorded; only naming a pinned category (above) writes the values listed for it. Outgoing calls made through `IHttpClientFactory` are logged with header values and query values redacted by the platform.

The raw request path is recorded: in the completion event (`RequestPath`), in the request scope of every framework event and in the `url.path` span attribute. It is kept because it finds the resource in an incident. Routes therefore carry opaque identifiers only, such as a UUID: never personal data (a national id, an email, a phone number, a name) and never a secret (tokens go in a header or in the body).

The one accepted exception to the rule is the unhandled-exception event: it holds the exception in full (message, inner exceptions, stack trace), and an exception message can quote the value that caused it. That is acceptable only because access to the logs is restricted and they are kept for a limited period; the deployment must provide both. Developers do not put personal data or secrets in the messages of exceptions they throw, and do not log a caught exception that wraps user input at Information or above. For the same reason the exception handler logs a request that could not be bound by its status only: the platform's message quotes the rejected value.

Code that logs follows the same rule: log identifiers, never credentials or personal data.

Clients can send trace context. An incoming `traceparent` chooses the trace id that appears in the logs and in the `traceId` of problem responses, and can turn sampling off for its request; incoming `baggage` is forwarded on outgoing HTTP calls. The reverse proxy should remove `traceparent`, `tracestate` and `baggage` from requests of public clients, and keep them only from trusted callers.

### Traces and metrics

OpenTelemetry records a server span per request, named after its route with `http.route` set (and, after authentication, `user.id` and `tenant.id` with the opaque GUIDs of the current user and tenant, each only when it is known), a client span per outgoing `HttpClient` call and a span per database command (Npgsql's `Npgsql` source, with `db.query.text`, `db.system.name`, `db.namespace`, `server.address`, `server.port`, `db.npgsql.data_source` and `db.npgsql.connection_id`; the statement text, never parameter values). A failed command adds `error.type` (the SQLSTATE for a server error, such as `22P02`, otherwise the exception type), `db.response.status_code` (the SQLSTATE, for a server error only) and the error status, whose description is the `error.type` value. Health probes produce no span, the readiness query included (it is recognized by its own command type, not by its text, so an application query that reads `SELECT 1` is still traced), and opening a physical connection is not traced (the `db.client.connection.create_time` metric measures it). No span holds exception text, from any source: an `exception` event recorded on a span keeps `exception.type` only (its message and stack trace are left empty, because they quote input values, user names and host names), and an error status description is replaced by the span's `error.type`. No header (the user agent included) and no query string is recorded; a client span keeps the scheme, host, port and path of its target only. Metrics: the ASP.NET Core server metrics (`http.server.request.duration` among them), the HTTP client metrics, the .NET runtime metrics and Npgsql's connection pool and command metrics, whose pool name is the application name. The resource names the service with the application name (`service.name`), its version (`service.version`) and its environment (`deployment.environment.name`); `OTEL_SERVICE_NAME` and `OTEL_RESOURCE_ATTRIBUTES` override them.

Nothing is exported until an OTLP endpoint is set; with none, the application starts, runs and stops without trying to send anything. The endpoint is not in `appsettings.json`: set it in the environment, for example to an OpenTelemetry Collector:

```sh
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4317     # traces and metrics, gRPC
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf                  # with port 4318, when the collector only accepts HTTP
```

`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` or `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` alone turns on that signal only. The other standard `OTEL_EXPORTER_OTLP_*` variables (headers, timeout) apply as usual. An unreachable collector does not affect requests and logs nothing; the spans of that interval are lost. Stopping the application waits for the last export to give up, up to the exporter timeout (`OTEL_EXPORTER_OTLP_TIMEOUT`, 10 seconds by default); keep it below the orchestrator's termination grace period (30 seconds by default in Kubernetes). Logs are not sent over OTLP; they stay on standard output.

Nothing is written to disk. `Serilog.AspNetCore` brings the file and debug sinks as transitive packages; they are inert, because sinks are configured in code and never read from configuration. The OTLP exporter writes to disk only if `OTEL_DOTNET_EXPERIMENTAL_OTLP_RETRY=disk` is set. Do not enable either.

### Adding a source or a meter

An `ActivitySource` or a `Meter` whose name starts with the project name followed by a dot (`MyApp.Sales`, for example) is collected with no registration:

```csharp
private static readonly ActivitySource Source = new("MyApp.Sales");
private static readonly Meter Meter = new("MyApp.Sales");
```

For any other name, a library's for example, register it once from the code that adds that library, before or after `AddTelemetry()`, as `src/MyApp.Api/DatabaseComposition.cs` does for Npgsql:

```csharp
services.AddTelemetrySource("Npgsql");
services.AddTelemetryMeter("Npgsql");
```

## Security settings

The API applies these protections to every request, in one fixed order set by `app.UseApiPipeline()` in `Program.cs` (the order and its reasons are in the XML documentation of that method):

1. **Forwarded headers**, only when a proxy is configured: the client address and scheme come from `X-Forwarded-For` and `X-Forwarded-Proto` sent by a trusted proxy.
2. **Security headers** on every response, errors included: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` (the API serves no HTML) and `Cross-Origin-Resource-Policy: same-origin` (other sites cannot embed a response with an image or script tag; CORS requests are governed by the CORS policy, not by this header). `Cache-Control: no-store` is added to every response that does not set its own, so no browser or shared cache keeps user data or tokens; an endpoint that wants caching sets `Cache-Control` itself. This includes the OpenAPI document (served outside Production only, so it is never stale); the health probes set their own `no-store, no-cache`. `Strict-Transport-Security: max-age=31536000; includeSubDomains` is added only to HTTPS requests for a host that is not `localhost`, `*.localhost` or a loopback address, and never in the Development environment, so a browser does not pin HTTPS on a development machine. Kestrel does not send the `Server` header.
3. **CORS**, only when an origin is listed. Preflight requests are answered by the API itself. While CORS is on every response carries `Origin` exactly once in `Vary`, next to any value an endpoint set (the platform only writes it when more than one origin is listed), so a shared cache never serves a response made for one origin to another.
4. **Error handling and routing** (see [Errors](#errors)).
5. **Rate limiting**: a fixed window per client address. A rejected request answers 429 `rate_limited` as a problem document with a `Retry-After` header in seconds. The health probes are never limited.
6. **Authentication, the authenticated-request steps, then authorization** (see [Authorization](#authorization)). `UseApiPipeline()` adds them and requires `AddApiAuthorization()`; it stops the application at startup without it. No `UseAuthentication()` or `UseAuthorization()` call in `Program.cs` is needed.

Authentication and authorization sit after routing, because the steps and authorization need the matched endpoint, and inside the error handling, so an anonymous request to a secured endpoint answers 401 `unauthorized` and an authenticated one without permission 403 `forbidden`, both as problem documents with the security and CORS headers. Placing them there also stops `WebApplication` from adding them on its own in front of the whole pipeline, before routing, where authorization sees no endpoint and every secured endpoint fails with a 500. They run after the rate limiter, so a flood of requests is rejected before any token is validated. The global limit is therefore per client address, never per user; a later per-user or per-tenant limit needs the authenticated identity, so it must be a separate limiter in an authenticated-request step, not a policy of this one. Operations that require authentication declare 401 in the API contract, and 403 when they require a permission; a fallback authorization policy is not endpoint metadata and does not add them.

The settings live in the `Http` section of `appsettings.json` and can be set per environment, for example with environment variables (`Http__Cors__AllowedOrigins__0=https://app.example.com`, one variable per list item). They are validated when the host starts: an invalid value stops it with an `OptionsValidationException` that names the setting.

| Setting | Default | Why this default |
| --- | --- | --- |
| `Http:Cors:AllowedOrigins` | empty: CORS off | Closed by default: with no origin listed no CORS header is written and only same-origin pages can call the API. Each entry is an origin exactly as a browser sends it, `scheme://host[:port]` with no path, no trailing slash and no default port (`https://app.example.com`, not `https://app.example.com:443`). Credentials (the refresh cookie) are allowed for listed origins, so `*` and any other wildcard are rejected, and an `http` origin is accepted only for `localhost`, a `*.localhost` name or a loopback address, or in the Development environment; anything else must be `https`. The Vite development server, `http://localhost:5173`, belongs in `appsettings.Development.json`, not in the settings of a deployed environment. |
| `Http:RateLimiting:PermitLimit` | `300` | Requests one client may send per window: about 5 per second on average, generous for a person using the application and low enough to slow down a script. Must be between 1 and 10,000 (no person or browser sends more in one window, so a higher value would switch the limiter off), and the limit divided by the window must not exceed 100 requests per second, for the same reason. |
| `Http:RateLimiting:Window` | `00:01:00` | Length of the fixed window. A minute smooths short bursts such as a page loading several resources. Must be between `00:00:01` and `01:00:00`: a rejected client may wait for the rest of the window, and a longer one turns a burst into a lockout. |
| `Http:RateLimiting:Auth:PermitLimit` | `10` | Requests one client may send per window to the sign-in, refresh, logout and change-password endpoints together, on top of the global limit: enough for a person who mistypes a password a few times, few for a script guessing passwords. Same bounds as `PermitLimit`. |
| `Http:RateLimiting:Auth:Window` | `00:01:00` | Length of the fixed window of the authentication limit. Same bounds as `Window`. |
| `Http:ForwardedHeaders:KnownProxies` | empty | IP addresses of the reverse proxies whose forwarded headers are trusted, such as `10.0.0.5` or `fd00::5`. Empty, the headers are ignored, so a client cannot choose the address that the rate limiter and the logs see. Rejected: an IPv4 address not written as four plain decimal octets from 0 to 255 without leading zeros (the platform reads `010.0.0.5` as octal, 8.0.0.5, and `0x0A` as hexadecimal, so such a value would silently trust another host); an IPv4-mapped IPv6 address such as `::ffff:10.0.0.5` (write the IPv4 form, `10.0.0.5`, which is how the platform matches IPv4 clients); anything that is not an IP address. |
| `Http:ForwardedHeaders:KnownNetworks` | empty | Networks of trusted proxies in CIDR notation, such as `10.0.0.0/8`, for proxies without a fixed address (containers, Kubernetes). Rejected: host bits that are not zero (`10.0.0.1/8`: either a single proxy or a network was meant, and guessing widens the trust); IPv4 not written as four plain decimal octets (as for `KnownProxies`); an IPv4 network wider than /8 (the largest private block; wider spans networks no deployment owns, up to `0.0.0.0/0`); an IPv6 network wider than /32 (the largest block a registry allocates to one operator; wider spans unrelated operators, up to `::/0`); an IPv6 network that overlaps the IPv4-compatible range `::/96` or the IPv4-mapped range `::ffff:0:0/96` (a dual-stack listener reports every IPv4 client as `::ffff:a.b.c.d`, so such a network, `::/32` for example, would trust the whole IPv4 internet); an IPv6 network that overlaps Teredo, `2001::/32`, or 6to4, `2002::/16` (anyone can obtain an address there). Overlap is computed from the prefixes, so a network that contains, or lies inside, one of these ranges is rejected. |

Behind a reverse proxy, list the proxy (or its network) in `KnownProxies` or `KnownNetworks`; otherwise every request appears to come from the proxy and all clients share one rate limit. The proxy must overwrite or append to `X-Forwarded-For` (not pass the client's value through unchanged); the API walks the list from the right and stops at the first address that is not a trusted proxy, so values a client writes to the left are ignored.

`ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` (some hosting platforms set it) makes the platform add its own forwarded headers middleware in front of the pipeline and clear the trusted lists, which on its own would trust `X-Forwarded-For` from anyone. With the variable set and no proxy configured the API refuses to start and says so: configure `Http:ForwardedHeaders` or unset the variable. With proxies configured the API's lists are applied after the platform's setup and win, so only the listed proxies are trusted either way.

CORS details, fixed in `HttpSecurityRegistration` because a JSON API needs no more:

- Allowed methods: `GET`, `POST`, `PUT`, `PATCH`, `DELETE` (plus `HEAD` and `OPTIONS`, which need no listing).
- Allowed request headers: `Accept`, `Accept-Language`, `Authorization`, `Content-Type`, `If-Match`, `If-None-Match`, `X-Tenant`.
- Headers a browser client may read besides the always-exposed ones: `Retry-After`, `ETag`, `Location`.
- Browsers may cache a preflight answer for 10 minutes.

The rate limit is partitioned by `HttpRateLimiting.ClientPartitionKey`: the client address after forwarded headers, with an IPv6 client counted by its /64 network so it cannot reset its limit by rotating addresses. A stricter limit for a group of endpoints (the authentication endpoints have one, `auth`) is a named policy added with `services.Configure<RateLimiterOptions>(o => o.AddPolicy(...))`, partitioned with the same key and required with `.RequireRateLimiting(name)` (it runs before authentication, so it can key on the address but not on the user); it applies on top of the global limit and its rejections get the same 429 answer. An endpoint that must never be limited is marked with `.DisableRateLimiting()`, which also removes the 429 from its entry in the API contract.

Limits of this setup, stated plainly:

- `/health/live` and `/health/ready` are public (they allow anonymous access, so the fallback authorization policy never applies to them, and the authenticated-request steps skip them) and never rate limited, and `/health/ready` runs the readiness checks (a query to the database) on every request. The reverse proxy must not expose `/health/*` to the internet; only the orchestrator should reach them.
- When the server listens on a Unix socket or a named pipe there is no remote address, so every client shares one rate limit partition. That setup is not supported with this limiter: listen on TCP behind the proxy and list the proxy as above.

## Data Protection keys

ASP.NET Core Data Protection (brought by the authentication) protects short-lived secrets such as the library's two-factor tokens with a key ring. The API keeps that ring in the shared database, table `data_protection.keys` (`DataProtectionComposition` in `src/MyApp.Api`, storage in `src/BuildingBlocks/MyApp.BuildingBlocks.Infrastructure/DataProtection/`), so every instance of the API uses the same keys, under the application name `MyApp`. The migrator creates the table and gives the application's login read and insert only (see [Database roles and deployment](#database-roles-and-deployment)).

Every key is encrypted at rest with a certificate before it is stored. Outside Development the certificate is required: the API checks it at start and does not start without a valid one, and the error names the setting, never a path. In Development it is optional: without it keys are stored unencrypted and the platform logs a warning at start.

| Setting | What it is |
| --- | --- |
| `DataProtection:Certificate:CertificatePath` | Path of the PEM certificate. Its key must be RSA, 2048 bits or more. |
| `DataProtection:Certificate:KeyPath` | Path of its PEM private key, not encrypted. |
| `DataProtection:PreviousCertificates:0:CertificatePath`, `...:0:KeyPath` | A certificate used before a rotation (`1`, `2`... for more): it only decrypts the keys it encrypted. |

A free self-signed certificate is enough:

```sh
openssl req -x509 -newkey rsa:3072 -nodes -keyout dataprotection.key -out dataprotection.crt -days 3650 -subj "/CN=MyApp Data Protection"
```

- Mount both files as secrets (a Kubernetes or Docker secret, a key vault mount) and give their paths, for example `DataProtection__Certificate__CertificatePath=/run/secrets/dataprotection.crt` and `DataProtection__Certificate__KeyPath=/run/secrets/dataprotection.key`. Never put them in the repository or in an `appsettings` file.
- It is not a TLS certificate: nobody else checks it, so it needs no certificate authority, and Let's Encrypt is not suitable (its certificates last 90 days and are meant for TLS).
- Rotation: create a new certificate, set it as `DataProtection:Certificate` and move the old one to `DataProtection:PreviousCertificates:0`. New keys are encrypted with the new certificate; keys encrypted with the old one stay readable while it is listed. Keep it listed at least 90 days after the rotation (a key's default lifetime) plus the lifetime of the longest-lived protected payload; after that nothing still needs the keys it encrypted.
- Signed rows. With a certificate, the API signs every row it stores with the current certificate's private key (RSA-PSS, SHA-256, over the friendly name and the XML) and keeps the signature and the certificate's SHA-256 thumbprint in `signature` and `signer`. It reads only rows signed by the current certificate or one of `DataProtection:PreviousCertificates`: a row the application's login could insert without the private key (unsigned, signed by an unknown certificate, or with a bad signature) is skipped with a warning (`DataProtectionKeyUnverified`) naming its id only. A row whose XML does not parse is skipped the same way (`DataProtectionKeyMalformed`). Without a certificate (Development only) rows are stored unsigned and all are read.
- Switching from no certificate to a certificate starts a new key ring: the unsigned keys are no longer read, and what they protected becomes unreadable.
- A rotation must keep the old certificate in `DataProtection:PreviousCertificates` as long as the keys it signed, or the data they protect, must stay readable: once it is removed, its rows fail the signature check and are skipped.
- Losing every certificate that encrypted a key makes that key unreadable, and with it whatever the key protected: keep a copy of the certificate and its key where the other production secrets are kept.
