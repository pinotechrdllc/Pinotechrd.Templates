# ADR 0008: The security library on tenant schemas selected by search_path

Status: accepted with conditions (spike `spikes/security-schema-per-tenant`, before phase 2). Date: 2026-11-18.

## Context
Phase 2 wires `Pinotechrd.Security` into the template on the schema-per-tenant design of ADR 0001: no schema in the model or the migrations, one cached EF model, and a connection interceptor that sets `search_path` to the current tenant's schema on one shared data source. The library's own tests use only the EF in-memory provider, so nothing had shown how its model, stores, refresh flow, HTTP behaviour, start-up checks and tenant middleware behave on PostgreSQL with that design. A failure here would change the Phase 2 plan before code depends on it.

## What was tested
- The published packages `Pinotechrd.Security` and `Pinotechrd.Security.Abstractions` `1.2.0-preview.2` from nuget.org (built from commit `cdacd4cf` of the library repository; file and line references below are to that commit). .NET 10.0.14, EF Core 10.0.15, Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3, EFCore.NamingConventions 10.0.1 (snake_case), Microsoft.AspNetCore.TestHost 10.0.15, Testcontainers.PostgreSql 4.17.0 with `postgres:17.7`.
- Command: `spikes/security-schema-per-tenant/run.ps1` (or `dotnet run --project spikes/security-schema-per-tenant/Spike/Pinotechrd.Spikes.SecuritySchemaPerTenant.csproj`). One run answers all six questions; the README of the spike lists each check and the setup.
- Catalog schema `catalog` with one plan (module `SALES` only), two active tenants `a` and `b`; tenant schemas `tenant_a` and `tenant_b` with modules `SALES` and `REPORTS`, three permissions, a role granted all three, one user in it, and in `a` only a per-user deny and an extra user. One `NpgsqlDataSource` with `Max Pool Size=4`.

## Results (measured)
Q1, the model. PASS.
- The library hard-codes two things in `PinotechrdSecurityDbContext.OnModelCreating`: the catalog schema `"public"` (`Data/PinotechrdSecurityDbContext.cs` line 98) and, for every tenant table and as default schema, the value of `ISchemaProvider.GetSchemaName()` (lines 141-181). Its `ModelSchemaCacheKeyFactory` keys the model by that schema (`Data/ModelSchemaCacheKeyFactory.cs` lines 17-19), but `AddPinotechrdSecurity` never registers it.
- Used as documented, with EF's default cache key: tenants `a` and `b` got the same model, and `b` saw `users` in `tenant_a`. With the factory registered by hand: a different model per tenant.
- Override measured: a context derived from `PinotechrdSecurityDbContext<AppUser, AppRole>` calls the base, then clears the default schema, sets no schema on the 11 tenant entities, puts the 5 catalog entities (`tenants`, `subscription_plans`, `system_subscriptions`, `subscription_plan_modules`, `subscription_plan_features`) in `catalog` and excludes them from migrations, and ignores the navigations `SubscriptionPlanModule.Module` and `SecurityModule.PlanModules`, which removes the only foreign key across catalog and tenant (line 128). A second context with the same remapping owns the catalog migrations and excludes the tenant tables. Both contexts receive a constant placeholder schema provider whose value never reaches SQL.
- Two scopes for tenants `a` and `b` got the same model instance. The tenant script (EF's model differ and SQL generator, the pair behind `migrations add` and `migrations script`) has 11 unqualified tables and names no schema; the catalog script has 5 `catalog.*` tables and no reference to a tenant table. The tenant script, run through the interceptor, created identical tables in `tenant_a` and `tenant_b`; `public` stayed empty.
- Cost: about 60 lines for the two contexts and the remapping, plus 34 for the interceptor. The fallback (an own context implementing `ISecurityDbContext`) was not needed and not built.

Q2, behaviour per tenant on one data source. PASS.
- 40 sequential and 80 parallel calls alternating `a` and `b`, on 4 physical connections, each saw only its own tenant: `current_schema()`, `UserManager.FindByNameAsync` (same user name, own id; a user of `a` invisible from `b`), `SecurityEngine.CanAccessAsync` (role grant true; per-user deny false in `a`, true in `b`; module not in plan false), `DbSecurityStore.GetActiveModuleCodesAsync` (the join of catalog plan modules to tenant modules) and the per-user overrides.
- Lockout through `PinotechrdAuthManager.LoginAsync`: two failures in `a` left `access_failed_count` 2 in `a` and 0 in `b`; after five, `a` answered `Account locked out` and `b` signed in. Login permissions: `a` = `SALES.VIEW`, `b` = `SALES.EDIT, SALES.VIEW`.
- No current tenant: the interceptor throws in `ConnectionOpening`, so `UserManager.FindByNameAsync` fails with `InvalidOperationException` before any SQL; nothing reached `public`.
- Reset on return to the pool: on a pool of one connection, after a tenant query, a raw open showed `search_path = "$user", public` (Npgsql's default reset on close, `DISCARD ALL`). With `No Reset On Close=true` it showed `tenant_a`.
- Also observed: `CanAccessAsync("Sales", "View")` is false while `("SALES", "VIEW")` is true; `SecuritySeeder.SeedModuleAsync` fails with PostgreSQL `23503` on `security_permissions`.

Q3, refresh. PASS.
- `IRefreshTokenStore` has `SaveAsync`, `ValidateAsync` and `RevokeAsync` and nothing that validates and revokes in one step (`IRefreshTokenStore.cs` lines 15-27). `PinotechrdAuthManager.RefreshAsync` calls `ValidateAsync` (line 183), then `UserManager.FindByIdAsync` (line 194), then `RevokeAsync` (line 197).
- 50 pairs of truly concurrent `RefreshAsync` calls with the same token: with a database store whose `ValidateAsync` is `UPDATE ... SET revoked_at = now() WHERE token_hash = $1 AND revoked_at IS NULL AND expires_at > now() RETURNING user_id, tenant_id`, exactly one succeeded in 50 of 50. With a store that validates with a `SELECT`: both succeeded in 50 of 50. With the library's default `InMemoryRefreshTokenStore`: both succeeded in 50 of 50.
- The manager does not compare the token's tenant with the current one (line 190): a token of `a` refreshed while the request's tenant was `b` failed with `User not found`, and the atomic store had consumed it. With no current tenant the refresh threw after consuming the token.

Q4, HTTP status codes. PASS.
- Registered schemes: the four Identity cookie schemes and `Bearer`; default authenticate, challenge and forbid all resolve to `Bearer` (the library sets authenticate and challenge after `AddIdentity`, `Extensions/SecurityExtensions.cs` lines 93-97; forbid falls back to challenge).
- Anonymous request to a protected endpoint with a valid tenant header: 401 with `WWW-Authenticate: Bearer`. Bearer token without the permission: 403. No redirect; no setting needed. With no tenant, an `/api` request gets 400 from the tenant middleware before authorization.

Q5, start-up. PASS.
- `AddPinotechrdSecurity` validates only the signing key, and does so inside the call, before `Build` (`Extensions/SecurityExtensions.cs` lines 48-56): `InvalidOperationException: PinotechrdSecurity requires a non-empty JWT secret.` for no delegate, a null value from an empty configuration, or whitespace; `JWT secret must be at least 32 characters.` for 18 characters. It reads no connection string; a context with no provider fails only on first use.
- `MinimumSecretLength` is a settable option (`Options/PinotechrdSecurityOptions.cs` line 34): with 8 the 8-character key was accepted and signing then failed with `IDX10653` (HS256 needs at least 128 bits). The length is counted in characters, not bytes.
- Build-time OpenAPI generation (`Microsoft.Extensions.ApiDescription.Server`, host started with no configuration) in `OpenApiProbe`: exit 1 with the exception above. With a random key registered only when the entry assembly is `GetDocument.Insider`: exit 0 and the document written.

Q6, tenant resolution (library gap L2). Documented, not gating.
- Reads, in this order (`Tenancy/TenantResolutionMiddleware.cs`): the claim `tenant_id` only when the user is authenticated (lines 79-82), the header `TenantId` (85-88), the JSON body property `tenantId` after buffering the whole body with no size limit (91-122), the query parameter `tenantId` (125-128). No path segment.
- Unknown tenant: 400, no content type, body `Invalid TenantId.` (140-141). Missing on a path that starts with `/api`: 400, `TenantId is required.` (146-150). Missing anywhere else: the request goes on with no tenant (153). `SkipPaths` is a raw prefix match (70): `/health` also skips `/healthy-admin`.
- Order matters: after authentication, a bearer of `a` with header `b` resolves `a`; with `UseTenantResolution` before `UseAuthentication`, it resolves `b`.

## Findings (judgement)
- The library can be used with schema-per-tenant as ADR 0001 designs it, without a fork, by overriding its model in the template. The override is small and the measured behaviour per tenant (identity, lockout, permissions, the catalog x tenant join) is correct on one shared data source.
- The library's own design (schema in the model, model cache key per schema) does not work as documented: without the factory, every tenant uses the first tenant's schema. Any project following the README today would cross tenants.
- The refresh flow is only safe with a store whose `ValidateAsync` consumes the token. The library's default store, and any store that follows the method names literally, lets a stolen and a legitimate refresh both succeed.
- The 401/403 behaviour needs no change. The start-up check is right in intent but runs too early for a host that generates its OpenAPI document at build time.
- The catalog maps plans to modules by module id, but each tenant schema has its own module rows. It only works if module ids are the same in every tenant, which nothing in the library ensures.

## Decision
- Model: the template derives two contexts from `PinotechrdSecurityDbContext<TUser, TRole>` with the remapping measured here: a tenant context (no schema, catalog excluded from its migrations) and a catalog context (schema `catalog`, its own history table in that schema, tenant tables excluded). No `ModelSchemaCacheKeyFactory`. The `ISchemaProvider` the library requires gets a constant placeholder.
- Interceptor: one singleton `DbConnectionInterceptor` reads the tenant from the context (the library's scoped `TenantContext`), fails in `ConnectionOpening` when there is none, validates the schema name and runs `SET search_path` to that schema only in `ConnectionOpened`. The reset is Npgsql's reset on close; `No Reset On Close` is never set. `ITenantStore` runs before a tenant is known, so it uses the catalog context.
- Refresh store: refresh tokens live in `catalog.refresh_tokens`, hashed, registered after `AddPinotechrdSecurity`; `ValidateAsync` consumes with `UPDATE ... RETURNING`, `RevokeAsync` is idempotent. The refresh endpoint sets the tenant from the token's row (a template-owned lookup by hash) before it calls `RefreshAsync`.
- HTTP: keep the library's defaults (401 and 403); `UseAuthentication`, then `UseTenantResolution`, then `UseAuthorization`, fixed in the web building block.
- Start-up: register the library with a random throw-away key only when the entry assembly is `GetDocument.Insider` (the check the template already uses for the database), so the build-time contract can be generated with no configuration; the real key stays required at run time.
- Permissions and modules: the template seeds modules itself, with the same module ids in every tenant, and writes permission policies in upper case. It does not use `SecuritySeeder`.

## Library gaps (work in the Pinotechrd.Security repository, not in the template)
Each item states the evidence and the smallest change that removes the need for a template workaround. Line references are to commit `cdacd4cf`.
1. Schemas in the model. `Data/PinotechrdSecurityDbContext.cs` line 98 (`"public"`) and lines 141-181 (default and per-table schema from `ISchemaProvider`). Change: protected virtual catalog and tenant schema names where `null` means "no schema", and a switch to exclude the catalog tables from the context's migrations.
2. Model cache key. `Data/ModelSchemaCacheKeyFactory.cs` lines 17-19 exist but `Extensions/SecurityExtensions.cs` (lines 33-117) never registers them; measured: the first tenant's model is reused for all. Change: once item 1 lands, drop schema from the model and the factory; until then, register it or document it as required.
3. Cross-schema foreign key. `Data/PinotechrdSecurityDbContext.cs` line 128 (`SubscriptionPlanModule.Module`). Change: remove the navigation and key; the stores already join by id.
4. Module identity across tenants. Plans map to `ModuleId` (`Entities/SubscriptionPlanMapping.cs` line 16; joins in `Core/DbSecurityStore.cs` lines 40 and 58) while `SecurityModule.Create` (`Entities/SecurityModuleAndPermission.cs` line 56) and `SecuritySeeder` (line 33) give each tenant random ids. Change: map plans to module codes, or create modules with deterministic ids.
5. Seeder on a relational database. `Core/SecuritySeeder.cs` lines 52-58 create permissions without `ModuleId`; measured: `23503` foreign key violation. Change: set `ModuleId` to the module's id.
6. Module code case. `Core/DbSecurityStore.cs` line 44 compares `mod.Code == moduleCode` in SQL, codes are upper-cased on creation (`Entities/SecurityModuleAndPermission.cs` line 58) and the policy name is split as written (`Authorization/PermissionAuthorization.cs` line 35); measured: `Sales.View` denied, `SALES.VIEW` allowed. Change: upper-case the module code in `PermissionRequirement`.
7. Refresh race and tenant binding. `Interfaces/IRefreshTokenStore.cs` lines 15-27 (no consume operation), `Core/PinotechrdAuthManager.cs` lines 183, 194 and 197 (validate, query, revoke), `Core/InMemoryRefreshTokenStore.cs` lines 39-58 (validate does not consume); measured: both refreshes succeed in 50 of 50 pairs with the default store. Line 190 takes the tenant from the token without comparing it with the current one. Change: a single consume operation in the contract (validate and revoke atomically) used by `RefreshAsync`, an atomic in-memory implementation, and a rejection when the token's tenant differs from the current `TenantContext`.
8. Start-up validation. `Extensions/SecurityExtensions.cs` lines 48-56 throw inside the registration call; `Options/PinotechrdSecurityOptions.cs` line 34 lets the minimum be lowered below what HS256 accepts, and the check counts characters. Measured: build-time OpenAPI generation fails with no configuration; 8 characters accepted, then `IDX10653` at signing. Change: validate the options with `ValidateOnStart` instead of in the call, with a fixed floor of 32 bytes of UTF-8.
9. Tenant resolution (L2). `Tenancy/TenantResolutionMiddleware.cs`: header, unbounded JSON body and query string are accepted as tenant sources (lines 85-128), including for an authenticated user whose token has no tenant claim; the answers are plain text with no content type (140-141, 146-150); only paths under a hard-coded `/api` are refused without a tenant (146); `SkipPaths` is a raw prefix match (70); the result depends on the order with `UseAuthentication`. Change: for authenticated requests take the tenant only from the claim and reject a disagreeing header; make body and query sources opt-in with a size limit; answer with problem details; match skip paths by segment; make the protected prefix configurable.
10. Fallback schemas without a tenant (read, not measured). `Tenancy/DbSchemaProvider.cs` lines 11 and 26 fall back to a shared `identity` schema when no tenant is resolved, and `Tenancy/TenantContext.cs` lines 16-18 derive the schema name without validating it. The template uses neither. Change: fail when there is no tenant, and validate the derived name.

## Consequences for the template
- Phase 2 keeps its plan; the tasks "Wire Pinotechrd.Security", "Schema per tenant" and "Refresh token store in the database" follow the decision above.
- The template carries a model override (about 60 lines), an interceptor (about 35 lines) and a refresh store, and drops the override and the store's tenant lookup when gaps 1-4 and 7 are fixed in the library.
- Tests the template must keep, because they fail when a gap or a workaround regresses: one model instance for two tenants; a tenant migration script with no schema; isolation with alternating tenants on one data source; the open failing with no tenant; exactly one of two concurrent refreshes; 401 and 403 without redirect; build-time contract generation with no configuration.
- Not covered by this spike, to verify when built: PgBouncer in transaction pooling (`SET LOCAL` inside the transaction, ADR 0001), several API instances, two-factor and password-reset flows, and an application that hands EF an already-open connection.
- Before the template references a stable library version, re-run this spike against it.
